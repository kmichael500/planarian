# Shared contracts

`client-routes.json` is the source of truth for browser routes that have been migrated to the shared client-route contract.

The migration is intentionally incremental. Routes present in the manifest must be consumed through the generated projections. React routes that have not yet been migrated may continue to use their existing inline definitions until they are converted.

The long-term goal is for every browser route to live in this manifest because any route may eventually need to be generated by backend code (for example, links in email or notifications).

This manifest does **not** define ASP.NET API endpoints. API routes remain owned by ASP.NET endpoint metadata and should be exposed to TypeScript through OpenAPI/client generation.

## Supported route shapes

The current generator supports static paths, one or more required full-segment parameters such as `:projectId`, and required query parameters declared in `queryParameters`. Path parameters are inferred from the path and must be unique within a route. Route names and parameter names must also be safe generated-code identifiers; names that would collide after C# type generation or parameters reserved by TypeScript/C# are rejected. Non-root paths use a canonical no-trailing-slash form, and route shapes that would be indistinguishable under React Router’s default case-insensitive matching are rejected.

Optional segments (`?`) and splat/catch-all routes (`*`) are intentionally rejected for now. Extend the manifest schema, generator, and generator tests together before migrating a route that needs either feature; this is safer than silently generating a URL builder with different semantics from React Router.

## Development workflow

Generated projections are committed for reviewability and so ordinary backend-only builds do not require Node. Normal frontend commands regenerate them automatically; `npm run generate:client-routes` remains available when an explicit regeneration is useful.

Before committing, verify the generator itself and confirm that both committed projections are current:

```sh
cd Planarian.Web
npm run check:client-routes
```

The check runs the repository-tooling unit tests first, then performs a no-write drift check. PR validation runs this before frontend tests/builds and the .NET build so stale generated routes fail early.

Normal frontend entry points do not require manual generation: `npm start`, `npm test`, and `npm run build` run the generator automatically through npm lifecycle hooks. `npm run deploy` builds first, so direct Static Web Apps deployment also regenerates before deployment. The local deployment script and API deployment workflows prepare the shared routes before the API is built because the API consumes the generated C# projection.

Do not add route generation to `dotnet build`: the generated C# projection is committed so ordinary backend-only builds remain independent of Node. CI and deployment validate or regenerate from the manifest at the cross-project boundaries instead.

Browser-route renames are rollout contracts because the web and API are deployed independently. When the backend can emit a browser URL, introduce the new web route while retaining the old route as a temporary alias, deploy the compatible web version, then deploy the backend that emits the new URL. Remove the old alias only after the old backend version can no longer be serving traffic or generating links.
